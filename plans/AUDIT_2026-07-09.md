# Audit kodu, testu a performance

Datum: 2026-07-09

Rozsah: backend Spring Boot, frontend React/Bun, Liquibase migrace, repository vrstva, testy.

## Executive summary

Repo je celkove ve slusnem stavu. Backend je domenove rozdeleny, ma realne service/controller/repository testy a kompletni backend `mvn verify` prosel proti Postgres/Testcontainers. Nejvetsi rizika nejsou P0 bugy, ale rostouci komplexita orchestrace a nekolik mist, kde se pred skalovanim vyplati upravit datovy pristup.

Hlavni zavery:

- Backend testy jsou stabilni: Surefire 489 testu, Failsafe 38 IT testu, 0 failure/error po spusteni s Dockerem.
- Frontend testy jsou stabilni, ale pokryti je uzke: 51 testu ve 4 souborech proti 79 TS/TSX souborum.
- Nejvetsi tridy jsou hlavne orchestrace: `CartService` 828 radku, `UserProductSearchPersistenceService` 738, `UserInventoryService` 634, `Ap2MandateService` 615.
- DB dotazy jsou obecne rozumne: pouzivaji se batch loady, `EntityGraph` u cart/order a pgvector/HNSW pro merchant semantic search.
- Performance rizika jsou hlavne over-fetch do pameti, indexy nepokryvajici `order by`, importni diff aktivnich merchantu v aplikaci a vice roundtripu pri enrichment persistenci.
- Chybi coverage gate a query-count/performance testy. Testy umi overit chovani, ale nechrani pred N+1/regresi v poctu SQL dotazu.

## Prioritizace

### P1: rozdelit `CartService`

Soubor: `backend/src/main/java/com/meant/api/module/cart/service/CartService.java`

`CartService` ma 828 radku a drzi prilis mnoho odpovednosti najednou:

- lifecycle cartu: create/get/update/cancel,
- checkout handoff a refresh,
- fulfillment default selection,
- mapovani requestu do UCP cart/checkout DTO,
- native checkout completion/cancel delegaci,
- import nakoupenych polozek do inventory.

Relevantni use-case bloky:

- cart lifecycle: radky 78-120,
- checkout/handoff: radky 122-164,
- update checkout + fulfillment retry: radky 166-225,
- completion/cancel: radky 304-348.

Doporuceni:

- Ponechat `CartService` jako tenky public facade pro controller.
- Vyjmout:
  - `CartCheckoutHandoffService` pro checkout/create/get/refresh handoff.
  - `CartCheckoutUpdateService` nebo `CheckoutFulfillmentSelectionService` pro fulfillment selection a line matching.
  - `CartInventoryImportService` pro `importCartInventory`.
  - `CartRequestFactory` pro `CreateCartRequest`, `UpdateCartRequest`, `CreateCheckoutRequest`.
- Refactor delat po malych krocich s existujicimi `CartServiceTest` a `CartControllerIT`, ne soucasne s behavioral zmenami.

Ocekavany efekt: nizsi blast radius pri checkout zmenach a mene rizika, ze uprava fulfillmentu rozbije create/update/cancel flow.

### P1: inventory dotazy potrebuji lepsi indexy pro filtrovane listy

Soubor:

- `backend/src/main/java/com/meant/api/module/user/service/UserInventoryService.java`
- `backend/src/main/resources/db/changelog/migration/016-add-user-inventory.xml`

`inventoryItems` vola strankovane repository metody s filtrem a `OrderByUpdatedAtDesc`:

- category + restock: radky 251-256,
- category: radky 258-263,
- restock: radky 265-268,
- all: radek 270.

Migrace ma indexy:

- `(user_id, updated_at)`,
- `(user_id, category)`,
- `(user_id, restock_enabled)`.

Problem: category/restock indexy nepokryvaji `order by updated_at desc`, takze Postgres muze filtrovat pres index, ale pak radit. Pri quota 500 je to zatim male, ale default/max list limity jsou 50/100 a roste to s budouci kvotou.

Doporuceni:

- Doplnit kompozitni indexy podle realnych endpointu:
  - `(user_id, category, updated_at desc)`,
  - `(user_id, restock_enabled, updated_at desc)`,
  - zvazit `(user_id, category, restock_enabled, updated_at desc)`.
- Po pridani indexu pustit `EXPLAIN (ANALYZE, BUFFERS)` na vsechny 4 varianty listu.

### P1/P2: product search cache nacita cele vysledkove okno do pameti

Soubor: `backend/src/main/java/com/meant/api/module/user/service/UserProductSearchPersistenceService.java`

Pozitivni: neni tu klasicke N+1. Recent products i explanations se nacitaji batch metodami:

- `findBySearchIdIn` na radcich 154-157,
- explanations pres `productKeyIn` na radcich 567-581 a 618-634,
- filter matches pres `explanationIdIn` na radcich 666-678.

Riziko: cached search nacita vsechny result itemy pro search a az pak dela page/visibility/ranking v Jave:

- `findBySearchIdOrderByRankAsc` radky 81-82,
- dalsi helper znovu umi nacist vse na radcich 345-346,
- `MAX_RESULT_WINDOW` je 100, takze to neni akutni, ale pri kazdem cached hitu jde do pameti cele okno.

Doporuceni:

- Kratkodobe: nechat, ale pridat query-count/performance test pro cached search.
- Strednedobe:
  - zvazit ulozeni final display ranku/visibility snapshotu pro cache key, aby slo strankovat v DB,
  - nebo zavest repository metodu pro rank window a nacitat jen `offset + limit + buffer`, pokud curation nepotrebuje cele okno.
- U recent products zvazit limit per search, aby `recentSearchLimit * 100` nerostlo bez kontroly.

### P2: `UserInventoryService` micha CRUD, import, photo recognition, scoring

Soubor: `backend/src/main/java/com/meant/api/module/user/service/UserInventoryService.java`

Trida ma 634 radku. Nejvic rizikove odpovednosti:

- CRUD/list/export: radky 77-158,
- import purchased items: radky 160-207,
- profile hash + recommendation signals: radky 210-245,
- category inference/similarity scoring dale v souboru.

Performance detail: `recommendationSignals` nacte vsechny inventory itemy uzivatele a pro kazdy product vola `signal(product, items)`, tj. O(pocet produktu * pocet inventory itemu). Pri dnesni kvote 500 a search okne 100 je worst-case porad zvladnutelny, ale je to misto, ktere poroste s novymi use-casy.

Doporuceni:

- Vyjmout `UserInventoryRecommendationSignalService`.
- Predpocitat normalizovana tokenova pole nebo aspon v jednom pruchodu vytvorit indexy podle `sourceProductKey`, category a restock flagu.
- Pro export ponechat cele nacteni, ale pro recommendation signals nepouzivat plny entity mapping, pokud bude stacit projekce.

### P2: merchant enrichment persistence dela vic DB roundtripu nez musi

Soubor: `backend/src/main/java/com/meant/api/module/merchant/service/MerchantEnrichmentPersistenceService.java`

Pri zmene profilu se:

- smaze 7 child kolekci po jedne: radky 173-180,
- capabilities se ukladaji po jedne uvnitr smycky: radky 199-223,
- requirements se ukladaji batchovane, ale batch je per capability, ne per merchant.

Pro batch enrichment to muze byt hodne SQL prikazu na jednoho merchanta.

Doporuceni:

- Nejdriv zmerit query count pro jeden merchant profile update s vice capabilities.
- Pak batchovat:
  - vytvorit vsechny capabilities do listu,
  - `saveAll(capabilities)`,
  - potom postavit requirements/extensions nad ulozenymi capabilities,
  - `saveAll(requirements)` jednou, `saveAll(extensions)` jednou.
- Pokud child rows rostou, zvazit DB-side delete pres FK a transactional replace porad ponechat kratky.

### P2: merchant import diffuje aktivni domeny v aplikaci

Soubory:

- `backend/src/main/java/com/meant/api/module/merchant/service/UcpMerchantImportPersistenceService.java`
- `MerchantRawRepository.java`
- `MerchantRepository.java`

`saveImport` ulozi aktualni dataset a pak oznaci chybejici merchanti jako inactive. Pri ne-prazdnem datasetu se ale nactou vsechny aktivni domeny z `merchant_raw` a `merchant`:

- `markMissingMerchantsInactive` radky 51-58,
- `MerchantRawRepository.findActiveDomains` radky 21-22,
- `MerchantRepository.findActiveDomains` radky 26-27.

Dnes to muze byt OK, ale pro vetsi katalog je to pametovy a sitovy prenos celeho aktivniho setu do aplikace.

Doporuceni:

- Pokud katalog zustane radove tisice zaznamu, ponechat a jen merit.
- Pokud poroste, pouzit DB-side staging tabulku nebo temp table pro latest import a `update ... where not exists (...)`.
- Alternativa bez temp table: import batch s `last_seen_at = fetchedAt` a nasledne `update active=false where active=true and last_seen_at < fetchedAt`.

### P2: embedding refresh query potrebuje EXPLAIN nad realnymi daty

Soubor: `backend/src/main/java/com/meant/api/module/merchant/repository/MerchantRepository.java`

Native query na radcich 48-74 hleda merchanty pro embedding refresh:

- `left join merchant_retrieval_embedding`,
- `exists` nad `merchant_category` nebo `merchant_popular_search`,
- stale/changed embedding podminky,
- `order by merchant.updated_at asc limit :limit`.

Riziko: existujici migrace maji `merchant(active)` index a unique constrainty na child tabulkach, ale query muze pri vetsim objemu profitovat z partial/composite indexu na aktivni merchanty podle `updated_at`.

Doporuceni:

- Pustit `EXPLAIN (ANALYZE, BUFFERS)` s realnym objemem.
- Zmerit variantu s partial indexem:
  - `merchant(updated_at) where active = true`,
  - pripadne pouzit materializovany flag "has retrieval content", pokud `exists` zacne dominovat.

## Test coverage audit

### Backend

Silne stranky:

- Dobre pokryte domain services: cart, user product search, user inventory, merchant enrichment, review, discount, order.
- Existuji controller IT pro klicove API cesty.
- Existuji repository IT pro order/review kandidaty a checkout state store.
- Testcontainers overuje Liquibase + Postgres/pgvector realne, ne jen H2.

Mezery:

- Neni coverage threshold, takze nelze rict, ktere casti jsou nepokryte.
- Velke orchestratory maji testy, ale slozitost tridy znamena, ze jednotlive private helper kombinace jsou kryte neprimo.
- Chybi query-count/performance testy.
- Chybi explicitni testy pro index-sensitive query plany; to neni unit test, ale aspon smoke `EXPLAIN` v doc/test helperu by pomohl.
- Sandboxovy `mvn test` bez Dockeru pada na Testcontainers. Pro lokaly/CI je to v poradku, ale pro rychly unit-only loop by se hodil profil/tag oddelujici DB testy.

Doporuceni:

- Pridat Maven profily nebo JUnit tags:
  - rychly unit/service test bez Dockeru,
  - DB integration test,
  - full verify.
- Pridat JaCoCo report a baseline.
- Pro DB kriticke cesty pridat testy na pocet dotazu nebo aspon loggable query metrics.

## Co je dobre zachovat

- Domenove rozdeleni backendu je celkove citelne a odpovida vetsine pravidel v `AGENTS.md`.
- Controller -> command/query -> service pattern je videt ve vetsine novych modulu.
- Remote I/O a DB persist jsou na nekolika mistech dobre oddelene, napr. merchant enrichment fetchuje remote data mimo persistence service a pak persistuje v kratke transakci.
- Search persistence se uz vyhyba trivialnimu N+1 pro explanations/filter matches.
- Cart persistence pouziva `@EntityGraph` pro lines a explicitne inicializuje applied codes.
- pgvector search je udelany pres JDBC a HNSW index, ne pres neefektivni JPA abstrakci.

## Navrzeny postup

1. Pridat JaCoCo report bez fail threshold, jen baseline.
2. Pridat query-count test pro cached product search a cart load.
3. Doplnit inventory composite indexy a `EXPLAIN` overeni.
4. Rozdelit `CartService` po jednom use-casu, bez behavioral zmen.
5. Vytahnout spolecne UCP dispatch helpery.
6. Zmerit merchant enrichment query count a podle vysledku batchovat capability/requirement persistenci.
7. Rozdelit frontend `ChatDiscoverView` a `MeantApp`, potom pridat komponentove testy pro nejrizikovejsi flow.

## Kratky zaver

Nenasel jsem akutni produkcni blocker. Nejvetsi hodnota dalsi prace je v kontrolovanem snizeni velikosti orchestration trid a v zavedeni metrik, ktere budou hlidat DB regresi. Soucasny test suite rika "chovani prochazi"; nerika ale "nezvysili jsme pocet dotazu" ani "tato cast je dostatecne pokryta procentualne". To je hlavni mezera auditu.
